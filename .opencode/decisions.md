# Решения

## 1. Общие правила в `public/shared/rules.mjs` (ESM)
Используются и сервером, и клиентом. Один источник правды по флоту/выстрелам -> невозможен рассинхрон
валидации. Файл лежит в `public/`, потому что браузер импортирует его напрямую (`./shared/rules.mjs`).

## 2. Сервер — источник истины в сетевом режиме
Клиент в сети не доверяет себе: не хранит флот соперника, отправляет только координаты выстрела,
`applyAttack` выполняется на сервере. Итог и состояние приходят в `state`.

## 3. `player.attacks` = выстрелы, полученные игроком
Следствие архитектуры п.2: `handleFire` пишет в `defender.attacks`, потому что атакуется именно защитник.
Поэтому в `stateForPlayer` поле `boards.self.attacks` содержит выстрелы **по своей** доске.
Это легко перепутать (клиент так и делал), поэтому зафиксировано здесь и в context.md.

## 4. Origin-проверка WS: в dev разрешены приватные подсети
`isOriginAllowed` в production пускает только явный `ALLOWED_ORIGINS` + домены Яндекса.
В development дополнительно пускаем `localhost`, `127.0.0.1`, RFC1918 и `*.local`,
чтобы игра работала по внутренней сети. Без этого сосед по LAN получал `403 Forbidden` на `/ws`
(браузер шлёт `Origin: http://192.168.x.x:3000`).
Безопасность не снижена в проде: ветка приватных сетей под `nodeEnvironment !== "production"`.

## 5. Комнаты и сессии в памяти
`rooms`, `sessions`, `quickQueue` — обычные Map/массивы. Достаточно для одной ноды/демо.
Ограничение зафиксировано: горизонтальное масштабирование потребует внешнего состояния.

## 6. Рематч требует согласия обоих игроков
`handleRematch` ждёт `players.every(p => p.rematch)`. Проверено E2E: реванш стартует
только после второго подтверждения, `round` инкрементируется, `attacks` обнуляются.

## 7. Rate limit на WS
Token bucket: 30 токенов, refill 12/сек (`consumeMessageBudget`). При превышении — RATE_LIMIT и close 1008.
Это защита от спама; при автоматизированном тестировании нужен темп < 12 сообщений/сек на сокет.

## 8. Тест «Промах» переведён на детерминированный флот
`(9,9)` — валидная клетка доски 10x10, и случайный флот мог её занять. Тест проверяет
определение промаха, а не случайность раскладки -> фиксированный флот вместо `createRandomFleet()`.

## 9. При возврате игрока состояние рассылается всей комнате
`reconnectPlayer` вызывает `broadcastRoomState(room)`, а не `sendState` только вернувшемуся.
Причина: соперник обязан узнать, что `opponent.connected` снова `true`.
Клиент блокирует выстрел при `!state.opponentConnected` (`fireOnlineAt`), поэтому без рассылки
бой у соперника выглядел мёртвым, хотя вернувшийся играл нормально.
Закреплено регресс-тестом `tests/reconnect.test.mjs` (поднимает реальный сервер на случайном порту).

## 10. Токен и признак активной комнаты — в `sessionStorage`
F5/reload сохраняет `sessionStorage`, поэтому переподключение после перезагрузки работает.
Закрытие вкладки — нет: клиент получает `ROOM_NOT_FOUND`. Известный компромисс, зафиксирован в tasks.md
как кандидат на перенос в `localStorage`.
## 5. Схема деплоя: подпуть `/sea-battle/` на существующем домене
nginx на хосте, все его `proxy_pass` на `localhost`, поэтому контейнер публикует
`127.0.0.1:8102:3000` (наружу не светится), а nginx срезает префикс `/sea-battle/`
и проксирует на этот порт. Страницу `sea-battle.html` отдаёт сам nginx из
`/var/www/sea-battle` — приложению сайта (8081) ничего менять не нужно.
Причина: сайт закрыт `location / -> localhost:8081`, статики у nginx нет,
а лезть в чужое приложение рискованно. Один origin => CORS не нужен.
Альтернативы (поддомен, iframe, CORS) описаны в `deploy/README-deploy.md`.

## 5. Схема деплоя: поддомен-префикс `/sea-battle/` вместо отдельного поддомена
Страница `sea-battle.html` лежит в веб-корне сайта, ассеты и WebSocket — на том же домене
по префиксу `/sea-battle/`, который срезается в nginx. Причина: один origin -> не нужен CORS
и не нужен отдельный сертификат/поддомен. Для случая «ассеты с чужого домена» оставлен
выключенный по умолчанию `CORS_ORIGINS` в `server.mjs`.

## 6. `dist/sea-battle.html` генерируется, а не копируется руками
`scripts/build-site-bundle.mjs` собирает страницу из `public/index.html`: пути ассетов ->
префикс, `config.js` -> inline-конфиг с адресом WS от `location.host`, плюс ссылка «на главную».
Причина: страница не должна расходиться с игрой, а домен в ней не должен быть зашит.
Скрипт падает с ошибкой, если в `index.html` изменились нужные фрагменты.

## 7. SDK Яндекс Игр не грузится вне Яндекса (`shouldLoadYandexSdk`)
На стороннем сайте SDK давал ошибки консоли («No parent to post message»,
«Can not get appId») и лишний запрос к yandex.ru. Причина: страница открыта не в плеере Яндекса,
поэтому SDK ей не нужен. Автоопределение: хост Яндекса, `window.parent !== window` (iframe/превью)
или localhost. Переопределяется флагом `SEA_BATTLE_CONFIG.yandexSdk`.

## 8. Мобильные размеры: тап-таргеты не меньше 44x44, шрифты не меньше 11 px
Проверено headless Chrome через CDP на 7 вьюпортах. Кнопки в шапке были 29–35 px по ширине,
бейджи — 10 px. Решено не «ужимать», а увеличить до рекомендуемых размеров, ценой небольшого
сжатия баннера на низких экранах (`min(100%, 460px)`, на низких 210px) — без обрезки картинки.

## 9. Основной проект остаётся под Яндекс Игры; деплой — отдельный слой
Игра не переводится на сайт asolontsov.ru. Всё, что нужно сайту, лежит вне `public/`:
`Dockerfile`, `docker-compose.yml`, `deploy/`, `scripts/build-site-bundle.mjs`,
а страница для сайта генерируется в `dist/` (в git игнорируется).
`public/index.html` и `public/game.js` не менялись — точка входа для Яндекс Игр
остаётся прежней, и архив для загрузки в Яндекс собирается из содержимого `public/`.
Единственный общий файл — `public/config.js`: для Яндекса в нём остаётся
`serverUrl: ""` (до публикации вписывается WSS-адрес), а страница сайта задаёт
конфиг inline и его не касается.
Проверено: `shouldLoadYandexSdk()` грузит SDK для games.yandex.ru, yandex.ru/com,
любого iframe (превью) и localhost; на asolontsov.ru без SDK (10 сценариев).
